❓ Comprehensive Technical Questions & Model Answers
Q1: Can you explain the exact cryptographic and settlement flow when an envelope arrives at your backend?
Assigned: Sourav Thakur (41523099) — Backend Architect
When an encrypted packet arrives at POST /api/v1/settle, the backend executes a 5-stage pipeline:
1. Wire-Hash De-duplication: It computes SHA-256 over raw wire bytes. If present in inMemoryWireCache, it returns the cached settlement response in under 0.5 ms.
2. Asymmetric Unwrapping: It invokes CryptoEnvelopeService, using our persistent RSA-2048 private key to decrypt the ephemeral AES key via RSA-OAEP with SHA-256 and MGF1 padding.
3. Symmetric Authenticated Decryption: It uses the decrypted 256-bit AES key to decrypt the payload with AES-256-GCM using the 96-bit IV and 128-bit authentication tag. If even 1 bit was altered, GCM tag verification throws a SecurityException.
4. Relational Idempotency Check: Within a READ_COMMITTED SQL transaction, it checks IdempotencyKeyRepository.existsBySenderVpaAndNonce(). If found, the transaction rolls back cleanly.
5. ACID Ledger Settlement: It acquires the sender account with optimistic locking (@Version), verifies balance >= amount, debits sender, credits payee, logs the transaction, saves the idempotency record, and commits atomically.
Q2: Why did you choose hybrid RSA-2048-OAEP + AES-256-GCM rather than pure RSA or pure AES?
Assigned: Sourav Thakur (41523099) — Cryptographic Systems
Hybrid cryptography gives us the best of both worlds:
• Why not pure RSA? RSA is computationally intensive and mathematically cannot encrypt data larger than its key size minus padding (a 2048-bit RSA key can only encrypt up to 190 bytes under OAEP-SHA256). Our JSON payment instruction is ~350 bytes, which exceeds pure RSA limits.
• Why not pure AES? Pure AES requires a pre-shared secret key. In an ad-hoc mesh where millions of strangers meet in a metro tunnel, sender phones cannot share a symmetric key with the central bank in advance without exposing it to intermediate sniffers.
• The Hybrid Solution: The client generates a fresh ephemeral 256-bit AES key, encrypts the arbitrary-length payment instruction under AES-GCM (which takes ~1ms), and encrypts only that 32-byte key under the Bank's RSA public key. Only the bank can decrypt the session key, and intermediate relays observe only opaque ciphertext.
Q3: How does your Dual-Tier Idempotency defense work, and why wasn't an in-memory cache enough?
Assigned: Sourav Thakur (41523099) — Concurrency & Database
A single-tier cache fails under two real-world failure modes:
• Failure Mode 1 (Memory Loss on Restart): An in-memory cache is lost if the server process restarts. If a bridge retries a gossiped packet after restart, a memory-only cache would re-execute the payment, double-debiting the sender.
• Failure Mode 2 (Concurrent Bridge Race Conditions): When two bridge devices exit a tunnel and hit 4G simultaneously, both submit identical packets in parallel threads. Two threads can check an in-memory cache at the exact same microsecond before either has written to it.
• Our Solution: Tier 1 (In-Memory ConcurrentHashMap) filters 99% of retransmissions in 0.28ms without hitting the disk. Tier 2 (Relational Database Unique Constraint on (sender_vpa, nonce)) guarantees ACID isolation: the second thread triggers a SQL DataIntegrityViolationException and rolls back cleanly with zero double-debit.
Q4: What is Delay-Tolerant Networking (DTN) and how does Store-Carry-Forward differ from TCP/IP?
Assigned: Sushant Sunder (41523103) — Mesh Routing Protocol
Traditional TCP/IP requires a continuous, synchronized end-to-end path: a packet moves from router to router along a live electrical circuit or radio wave within milliseconds. If any intermediate link drops, TCP aborts with connection timeouts.
Delay-Tolerant Networking (RFC 4838) operates on the Store-Carry-Forward paradigm: intermediate nodes accept encrypted packets, store them in persistent local buffers (IndexedDB on phones), carry them as citizens walk through physical corridors, and forward them whenever a new peer enters radio range (10–30m over Bluetooth LE). Communication occurs asynchronously over minutes or hours until reaching a bridge.
Q5: How does your epidemic gossip protocol prevent infinite message loops and buffer exhaustion?
Assigned: Sushant Sunder (41523103) — Mesh Routing Protocol
Pure epidemic routing replicates packets to every discovered peer, which in a dense metro station would quickly cause radio collision storms and flash memory exhaustion. We engineered three bounded mechanisms:
1. Integer Hop/TTL Decrement: Packets are initialized with $TTL = 10$ and $Hops = 0$. Every relay decrements TTL by 1 and increments Hop count by 1. When $TTL ≤ 0$, the packet is permanently purged from memory.
2. Ring-Buffer Hash De-duplication: Each device maintains a 500-element ring buffer of SHA-256 hashes of seen packets. If Carol already holds packet $P_1$, she rejects Dave's gossip offer in the initial handshake.
3. Opportunistic Bridge Prioritization: Nodes prioritize forwarding toward peers flagged with high mobility or bridge capability.

Q7: How do you ensure the user's PIN is never exposed in plaintext in browser memory or storage?
Assigned: Rajat Trehan (41523078) — Client Cryptography Enclave
In offlineCrypto.js, when the user inputs their 4-digit PIN on the simulated mobile keypad, we immediately derive:
pinHash = SHA-256(pin + ":" + senderVpa)
The cleartext PIN variable is immediately discarded from memory. Only the cryptographic hash is placed into the JSON instruction payload before AES-GCM encryption. Even if an attacker attaches a memory debugger to the device after transmission, the cleartext PIN cannot be recovered.
Q8: How do you mathematically prevent double-spending in a completely disconnected mesh?
Tough Grill Question — All Candidates
In a disconnected network, absolute real-time global consensus without communication is mathematically impossible (Fischer-Lynch-Paterson Theorem). MeshPay handles this through a hybrid economic and cryptographic risk model aligned with RBI guidelines:
1. Bounded Transaction Exposure: In accordance with RBI Circular DPSS.CO.PD.No.S-526/02-14-003/2021-22, offline transactions are strictly capped at ₹500 per transaction and ₹2,000 cumulative balance. An attacker cannot cause systemic bank collapse.
2. Sequential Bank Clearing: The Central Bank processes envelopes in order of arrival. The first merchant's envelope to reach a bridge consumes the ₹500 balance. The second packet is marked FAILED (INSUFFICIENT_FUNDS).
3. Future Hardware Enclave (eSE): In our future scope (Section 6.3), we document how smartphone hardware Secure Elements (eSE) can enforce monotonic on-device sequence counters, cryptographically preventing a second packet from ever being signed offline.
Q9: Why not use existing USSD (*99#) or UPI 123PAY instead of MeshPay?
Tough Grill Question — All Candidates
• USSD (*99#) uses GSM 2G voice signaling. It still requires a connection to a cellular cell tower. In underground subway tunnels or deep concrete basements, there is zero GSM signal, so USSD returns 'Network Error'. Furthermore, USSD suffers from >35% transaction failure rates and high carrier session costs.
• UPI 123PAY relies on IVR voice calls or ultrasonic sound waves. IVR requires live telecom voice coverage, which fails underground. Ultrasonic proximity sound waves only work point-to-point over 10 centimeters and cannot gossip packets across a 500-meter transit platform to reach an exit bridge.
• MeshPay requires zero cellular infrastructure at the payment location. It leverages the ambient Bluetooth LE radios of passing citizens to carry packets to the nearest exit.
